If your last hands-on frontend work involved jQuery selectors and a page reload on every click, most
of what you will hear in a design review now is unfamiliar vocabulary wrapped around ideas you
already understand: a page is still HTML, styled by CSS, made interactive by JavaScript. What
changed is how those three are organised and assembled before they reach a browser. This lesson
builds that model from the ground up.

## Why this exists

A browser only ever does three things: parse HTML into a structure (the DOM), apply CSS to decide
how it looks, and run JavaScript to change either one in response to events. Every framework, every
build tool, every architecture diagram with "frontend" in a box ultimately compiles down to those
three things. The complexity in modern frontend work exists because a banking web application is not
one page — it is dozens of screens sharing components, state, and data, updated by a team of people
who all touch the same code, and it must keep working as the business adds features for years.

A 2005-era site solved "many screens" by having the server render a full HTML page per URL. Every
click was a round trip: request, full-page HTML response, browser repaints everything. jQuery's job
was to patch that model — reach into the DOM after the page loaded and change a few things without a
full reload. That was a workaround bolted onto a page-at-a-time architecture. The component model,
which is what React, Angular and Vue all implement in different ways, throws out the "page" as the
unit of work and replaces it with reusable pieces of UI that manage their own markup, styling hooks
and behaviour together.

:::manager
When you hear "frontend architecture" now, it almost always means: how is the UI decomposed into
components, how does state flow between them, and how is data fetched from the API. It rarely means
which pages exist — pages are usually just components composed together by a router.
:::

## HTML, CSS and JavaScript: what each one owns

**HTML** describes structure and meaning: this is a heading, this is a list, this is a form field.
**CSS** describes presentation: colour, spacing, layout, what happens on hover. **JavaScript**
describes behaviour: what happens when the user does something, and what data is shown.

The discipline that has not changed in twenty years: do not make one language do another's job.
Putting layout logic in JavaScript (`element.style.left = x + 'px'` on every frame) or burying
business rules in CSS selectors both eventually collapse under their own cleverness. The correct
split still holds; only the tooling that enforces it has changed.

:::engineer
```html
<!-- structure -->
<button class="btn-primary" id="submit-payment">Submit payment</button>
```
```css
/* presentation */
.btn-primary { background: #0a5; color: white; padding: 8px 16px; border-radius: 4px; }
```
```javascript
// behaviour
document.getElementById('submit-payment').addEventListener('click', () => {
  submitPayment();
});
```
This is exactly what a React component does underneath — it just writes and owns all three together
per component rather than scattering them across three global files.
:::

:::manager
When a team says a page is "hard to change", ask which of the three is tangled with another. Inline
`style` attributes generated by JavaScript, or CSS selectors that encode business logic (`.status-3
{ display: none }` meaning "hide rejected payments"), are both signs the split has broken down.
:::

## The component mental model

A **component** is a self-contained, reusable piece of UI: its markup, its styling hooks and its
behaviour, described together, that can be placed anywhere and configured with **props** (the
values passed into it, like arguments to a function) and **state** (data the component owns and can
change over time, which causes it to redraw itself).

Think of a `PaymentRow` component in a transactions list: it takes a payment (props) and renders an
amount, a status badge and a "reverse" button. If the row also needs to track "is the confirmation
dialog open" — that is local state, private to that row, invisible to its siblings.

The critical shift from page-based thinking: instead of one big template for "the transactions
page", you compose `TransactionsPage` from `TransactionsTable` from many `PaymentRow`, each
independently testable and independently owned. Change how a status badge looks, and you change one
component used everywhere it appears, instead of hunting every page that renders one.

:::engineer
```jsx
function PaymentRow({ payment }) {              // props in, one argument
  const [confirming, setConfirming] = useState(false);   // local state
  return (
    <tr>
      <td>{payment.amount}</td>
      <td><StatusBadge status={payment.status} /></td>   {/* a component inside a component */}
      <td>
        <button onClick={() => setConfirming(true)}>Reverse</button>
        {confirming && <ConfirmDialog onConfirm={() => reverse(payment.id)} />}
      </td>
    </tr>
  );
}
```
`useState` is the hook that gives a function-shaped component memory across redraws. Calling the
setter (`setConfirming`) tells the framework "redraw this component with the new value."
:::

:::callout{kind=tip title="Component = the new unit of ownership"}
In an org chart sense, a component is often what one developer or one small team owns end to end:
its markup, style and behaviour, plus its tests. This maps cleanly onto a team topology — expect to
see component libraries ("design systems") owned centrally and consumed by feature teams.
:::

## State: the thing that actually gets complicated

State is any data that can change and that affects what is rendered: form input, whether a modal is
open, the list of transactions fetched from the API, whether that fetch is still loading. The hard
part of frontend engineering is not drawing pixels; it is keeping state consistent as it flows
between components, and as it goes stale relative to the server.

Two broad categories matter for a review:

- **Local state** — owned by one component, invisible elsewhere (a text field's current value).
- **Shared / global state** — needed by many components (the logged-in user, the current
  transaction filter). Passed down explicitly ("prop drilling") for small apps, or held in a shared
  store (Redux, Zustand, React Context, or newer server-state libraries) for larger ones.

A third category, often forgotten in estimates: **server state** — data that lives on the backend
and is only cached in the browser. It can go stale, fail to load, or be edited by someone else at
the same time. Treating server state like local state (fetch once, keep in a variable forever) is
the single most common source of "the screen shows the wrong balance" bugs.

:::manager
When reviewing a frontend design, ask explicitly: "where does the state for X live, and who else can
change it while this screen is open?" A screen showing an account balance that never refetches is a
correctness bug waiting for a support ticket, not a UI nicety.
:::

:::engineer
```javascript
// naive: fetched once, never refreshed, no error or loading handling
const [balance, setBalance] = useState(null);
useEffect(() => { fetch('/api/balance').then(r => r.json()).then(setBalance); }, []);
```
Production code adds loading state, error state, retry, and a strategy for staleness (poll, refetch
on window focus, or invalidate on a websocket event). Libraries like React Query / TanStack Query and
SWR exist specifically to handle this instead of hand-rolling it per screen — see the Intermediate
lesson.
:::

## The build step: why source code cannot just run

A modern frontend project is not shipped as the files a developer edits. The **build step** (bundling
and transpiling) exists for three real reasons:

1. **Browsers cannot parse JSX or TypeScript.** Source is transpiled to plain JavaScript.
2. **Hundreds of source files become a small number of optimised bundles.** A browser fetching 400
   individual files is slower than fetching a few merged, minified ones.
3. **Dependencies need resolving.** `import { useState } from 'react'` has to be turned into
   something the browser can actually fetch and run.

Tools that do this: webpack (older, still common in large existing codebases), and newer, faster
tools — Vite, esbuild, Turbopack — that have mostly replaced it for new projects since around 2021.
The output of the build step is a `dist/` or `build/` folder of static HTML, CSS and JS files, which
is what actually gets deployed — see the Deployment topic.

:::manager
"The build is broken" is an engineering-hours cost, not a production outage, as long as it is caught
before merge (CI should run the build on every pull request). If it is only caught at deploy time,
that is a process gap worth asking about.
:::

:::engineer
```bash
npm run build        # or: pnpm build / yarn build
# runs the bundler, type-checks (if TypeScript), outputs static files to dist/
```
The `package.json` `scripts` block defines what "build" actually runs. There is no single universal
command — it is project-specific configuration, usually Vite or webpack under the hood.
:::

## Common mistakes

- **Assuming "frontend" means "just styling".** State management, data fetching and error handling
  are most of the engineering effort; visual work is a fraction of it.
- **No loading or error states in the design.** Every screen that fetches data has at least three
  states — loading, error, success — and estimates that only account for the success state slip.
- **Treating the build step as an afterthought.** A project with no CI build check will discover
  breakage in production.
- **Ignoring accessibility from day one.** Retrofitting keyboard navigation and screen-reader support
  onto an existing component tree is far more expensive than building it in. Covered in depth in
  Intermediate.
- **Conflating "component" with "file".** A component is a unit of UI and behaviour; how it is split
  across files is a style choice, not the definition.

:::callout{kind=bank-context}
Customer-facing banking UIs are usually in scope for accessibility regulations (e.g. WCAG-aligned
requirements referenced by many national accessibility laws) and for change-control the same way
backend services are — a frontend release still needs a CAB-approved change record if it touches a
regulated customer journey, even though "it's just the UI" is a common (wrong) assumption.
:::

## Putting it together

::::exercise{id=ex-decompose-screen type=design title="Decompose a statement screen"}
You are reviewing a design for a screen that shows a customer's account statement: a date-range
filter, a running balance, a scrollable list of transactions, and a "download PDF" button. Sketch the
component breakdown: what are the components, what props does each need, what state is local vs
shared vs server state, and where does data fetching happen?
:::solution
- `StatementPage` — owns the date range as shared state (needed by both the filter and the fetch),
  and triggers the server-state fetch when the range changes.
- `DateRangeFilter` — local state only while the user is picking, calls back up to `StatementPage`
  once a range is confirmed (does not own the "current" range itself).
- `TransactionList` — receives transactions as props (server state, owned by the page); local state
  only for things like "which row is expanded".
- `TransactionRow` — receives one transaction as props; no state needed if purely presentational.
- `RunningBalance` — derived value, not its own state — computed from the transactions already
  fetched, or fetched separately if the backend provides it directly.
- `DownloadPdfButton` — local state for "is the download in progress"; triggers a separate request,
  not tied to the list's server state.
- Data fetching: one server-state fetch at the `StatementPage` level keyed by the date range, with
  loading and error states, not one fetch per row.
- A reviewer should ask: what happens if the date range changes while a download is in progress? Is
  the balance guaranteed consistent with the visible transaction list?
:::
::::
